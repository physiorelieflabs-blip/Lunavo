# TS COMMERCE — PAYMENT SYSTEM + TS AI IMAGE GENERATION

Implement the following requirements as core TS Commerce functionality. Do not omit, simplify, replace, or contradict any requirement below.

---

# PART A — TS PAY PAYMENT INFRASTRUCTURE

## 1. MULTIPLE CUSTOMER PAYMENT METHODS

Do NOT make bank transfer the single customer payment option.

Customers must be able to pay merchants using whatever legitimate payment methods are available for that customer, country, currency and transaction, including where supported:

* Debit card
* Credit card
* Bank transfer
* USSD
* Mobile money
* Digital wallets
* Account-based payments
* QR payments
* Other supported local payment methods
* Other supported international payment methods

The checkout must automatically display the payment methods that are actually available.

A customer must not be forced to use bank transfer when another supported payment method is available.

---

# 2. UNIQUE PAYMENT CODE FOR EVERY STORE

Every TS Commerce store must automatically receive a unique permanent **TS Pay Store Code**.

Example:

`TS-STORE-847291`

The code must uniquely identify that store inside TS Pay.

Every store must have its own code.

The system must never rely only on a merchant's bank account, email address or manually entered information to identify the destination store.

---

# 3. HOW THE STORE CODE WORKS

The customer should normally NOT need to manually type the store code when paying through the store's normal checkout.

The system should automatically attach the correct Store Code to the payment session.

For example:

**ABC Fashion**

Store Code:

`TS-ABC-847291`

Customer opens ABC Fashion's checkout.

They choose:

**Card**

Flutterwave processes the payment.

TS Commerce receives/validates the transaction and identifies:

`TS-ABC-847291`

The payment is then associated with:

**ABC Fashion → Merchant Balance**

The same principle applies when the customer chooses bank transfer, USSD, wallet or another supported payment method.

The payment method can change.

The destination store does not.

---

# 4. CENTRALIZED PAYMENT FLOW

The required architecture is:

**CUSTOMER**

↓

**SELECTS ANY SUPPORTED PAYMENT METHOD**

↓

**FLUTTERWAVE / APPROVED PAYMENT RAIL**

↓

**TS PAY TRANSACTION VERIFICATION**

↓

**TS PAY LEDGER**

↓

**CORRECT STORE'S TS COMMERCE BALANCE**

↓

**MERCHANT WITHDRAWAL REQUEST**

↓

**VERIFIED MERCHANT PAYOUT DESTINATION**

Do NOT design normal TS Commerce checkout as:

**Customer → Merchant's ordinary bank account**

The merchant's ordinary bank account is a payout destination, not the normal checkout destination.

---

# 5. EVERY PENNY MUST BE TRACEABLE

"Every penny must go through the dashboard" means every transaction must be represented inside the TS Commerce financial system and assigned to the correct store.

No successful customer payment may disappear outside the TS Pay transaction and ledger system.

Every financial movement must have a complete record.

Every transaction should include:

* Unique transaction ID
* Merchant ID
* Store ID
* Store Code
* Order ID
* Customer/order reference
* Payment method
* Amount
* Currency
* Gross amount
* Fees
* Taxes where applicable
* Discounts where applicable
* Payment-processing cost where applicable
* TS Commerce fee
* Net merchant amount
* Transaction status
* Settlement status
* Timestamp
* Related ledger entries
* Audit history

---

# 6. MERCHANT STORE BALANCE

Every store must have its own financial account/ledger inside TS Commerce.

The merchant dashboard must show:

* Available Balance
* Pending Balance
* Reserved Balance
* Gross Sales
* Successful Payments
* Failed Payments
* Refunds
* Chargebacks
* Taxes
* Shipping collected
* Discounts
* Payment costs
* TS Commerce fees
* Marketplace fees where applicable
* Merchant Net Balance
* Withdrawal Requests
* Completed Withdrawals
* Reversed Withdrawals
* Transaction History

The displayed balance must come from real server-side ledger/accounting records.

The frontend must never be able to directly change a merchant's balance.

---

# 7. FINANCIAL LEDGER

Build TS Pay around a proper auditable financial ledger.

Every financial event must create a corresponding ledger record.

Examples:

* Payment initiated
* Payment authorized
* Payment successful
* Payment failed
* Payment cancelled
* Payment expired
* Refund
* Partial refund
* Chargeback
* Chargeback reversal
* Fee
* Tax
* Reserve
* Reserve release
* Merchant withdrawal request
* Withdrawal approval
* Withdrawal rejection
* Withdrawal completion
* Withdrawal reversal
* Currency conversion
* Financial adjustment

Financial history must not be silently overwritten.

Corrections should create new accounting records and an audit trail.

---

# 8. FLUTTERWAVE INTEGRATION

Use **Flutterwave as the initial real payment processor/payment rail** for TS Commerce.

Use the **Flutterwave API credentials previously provided in the conversation/project/session** for this implementation when they are actually available to the development environment.

Do NOT ask for the credentials again when they are already available.

Do NOT invent credentials.

Do NOT create fake payment functionality and pretend it is connected.

If the credentials are not actually available to the development environment, implement the secure configuration structure and clearly leave the integration waiting for the real credential rather than fabricating one.

---

# 9. FLUTTERWAVE SECURITY

The Flutterwave secret/API credentials must:

* Never be exposed in frontend code
* Never be placed in publicly accessible JavaScript
* Never be committed to GitHub/source control
* Never be shown to merchants
* Never be displayed in logs
* Never be returned in API responses
* Be stored in secure backend environment variables/secrets
* Be used through server-side requests for protected operations

Validate payment status server-side.

Use secure webhook validation/signature verification where applicable.

Use idempotency and duplicate-processing protection.

Never credit a merchant merely because the frontend says a payment succeeded.

---

# 10. FLUTTERWAVE PAYMENT VERIFICATION

When Flutterwave reports a successful payment:

1. Receive the notification securely.
2. Verify the payment on the backend.
3. Verify the transaction with Flutterwave where applicable.
4. Verify the expected amount.
5. Verify the expected currency.
6. Verify the expected order/store.
7. Verify the Store Code.
8. Prevent duplicate processing.
9. Mark the payment appropriately.
10. Create the TS Pay ledger entries.
11. Credit the correct merchant/store balance.
12. Update the order.
13. Update the merchant dashboard.

The system must not credit the merchant solely from untrusted frontend data.

---

# 11. PROVIDER-INDEPENDENT TS PAY ARCHITECTURE

Flutterwave is the initial payment provider.

However, TS Pay must remain an abstraction/orchestration and accounting layer rather than becoming permanently hard-coded around Flutterwave.

Architecture:

**TS Checkout**

↓

**TS Pay Payment Orchestrator**

↓

**Payment Provider Adapter**

↓

**Flutterwave**

↓

**TS Pay Verification**

↓

**TS Pay Ledger**

↓

**Merchant Store Balance**

This must allow additional payment providers/rails to be added later without rebuilding the merchant ledger, balances, transaction history, payouts or dashboards.

---

# 12. MERCHANT WITHDRAWALS

Merchants must NOT automatically receive customer money directly into their bank account after every sale.

Instead:

**Customer pays**

↓

**Payment verified**

↓

**TS Pay ledger updated**

↓

**Merchant balance updated**

↓

**Funds become eligible after applicable settlement/risk rules**

↓

**Merchant requests withdrawal**

↓

**TS Commerce checks eligibility**

↓

**Withdrawal is processed**

↓

**Merchant receives money at verified payout destination**

The merchant dashboard must contain a clear:

**Withdraw Funds**

function.

Support configurable:

* Minimum withdrawal amount
* Settlement delay
* Pending period
* Reserve
* Risk holds
* Fraud review
* Chargeback exposure
* Refund exposure
* Daily limits
* Weekly limits
* Monthly limits
* Manual approval
* Automatic approval
* KYC requirements

Do not allow withdrawal of funds that remain pending, reserved, disputed or otherwise unavailable.

---

# 13. MERCHANT PAYOUT DESTINATION

Merchants must provide an eligible verified payout destination.

Depending on supported jurisdictions and payment infrastructure, this may be:

* Bank account
* Other legally supported payout destination

The payout destination must be separate from the normal customer checkout flow.

---

# 14. REFUNDS AND CHARGEBACKS

Refunds and disputes must update the correct merchant ledger.

Example:

Customer pays `$100`.

Later `$40` is refunded.

The system must create a separate refund entry and correctly adjust the merchant's available/settled balance.

Chargebacks must also be reflected in the merchant ledger.

If applicable and legally permitted, the system must handle situations where a merchant has already withdrawn money before a refund or chargeback occurs.

---

# 15. PLATFORM MONEY VS MERCHANT MONEY

Keep completely separate accounting classifications for:

**Merchant Funds**

**TS Commerce Revenue**

**Pending Funds**

**Reserved Funds**

**Payment Costs**

**Refunds**

**Chargebacks**

The system must always be able to determine:

* How much the customer paid
* Which store received the sale
* How much belongs to the merchant
* How much belongs to TS Commerce
* How much went to processing costs
* How much was refunded
* How much is pending
* How much is reserved
* How much is currently withdrawable
* How much the merchant has already withdrawn

# 19. MERCHANT SUBSCRIPTION PAYMENT

Merchant subscription payments to TS Commerce must also support normal available payment methods.

A merchant should be able to pay the TS Commerce subscription through supported methods such as:

* Card
* Bank transfer
* Other available payment methods

The subscription payment must be recorded separately as **TS Commerce platform revenue**.

Merchant funds and TS Commerce subscription revenue must never be mixed.

# PART B — TS AI + IMAGE GENERATION

# 22. TS AI

Create a built-in AI assistant called:

**TS AI**

Use **DeepSeek as the primary AI intelligence/reasoning engine**.

Do NOT use Pollinations as the primary chatbot/reasoning AI.

The architecture is:

**User → TS AI → DeepSeek → Response**

---

# 23. DEEPSEEK WITHOUT REQUIRED API KEY

Where technically feasible, design TS AI to use a **self-hosted/open-weight DeepSeek model** so that TS Commerce's core AI functionality does not require a DeepSeek API key.

Do not confuse "no API key" with "no model/infrastructure."

The application must actually use an AI model/inference engine.

Do not fake intelligence using predefined responses.

Design the AI model layer so the underlying model can be upgraded or replaced later.

### Payments

**Customer**

→ **Flutterwave**

→ **TS Pay**

→ **Verified transaction**

→ **Correct Store Code**

→ **Correct merchant ledger**

→ **Merchant balance**

→ **Merchant withdrawal**

→ **Verified payout destination**

### AI

**User**

→ **TS AI**

→ **DeepSeek**

→ Intelligent response

### Images

**User**

→ **TS AI**

→ **DeepSeek understands/refines request**

→ **Pollinations generates image**

→ **Save to Media Library**

→ **Download**

→ **Export to any authorized store**

### Fundamental rule

**Every payment must be traceable.**

**Every merchant/store must have its own TS Pay Store Code.**

**Customers can use normal supported payment methods, not bank transfer only.**

**Customer checkout money must flow through the TS Pay/payment infrastructure rather than directly to the merchant's ordinary bank account.**

**Merchant balances must remain separately accounted for.**

**Merchants withdraw eligible funds through TS Commerce.**

**Merchant subscription payments also go through the TS Commerce payment system and are recorded as platform revenue.**

**DeepSeek is the primary TS AI intelligence/reasoning engine.**

**Pollinations is the image-generation engine.**

**Generated images can be saved, downloaded, reused and exported to any store the user is authorized to manage.**

Build these requirements into the core architecture from the beginning rather than adding them as superficial frontend features later.
